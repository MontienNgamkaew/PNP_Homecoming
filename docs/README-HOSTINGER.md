# ติดตั้งบน Hostinger Business Web Hosting

คู่มือนี้ใช้กับชุด PHP + MySQL สำหรับเว็บไซต์คืนสู่เหย้าศิษย์เก่าการอาชีพพนมไพร การอัปโหลดชุดนี้ยังไม่ใช่การยืนยันว่าเปิดรับเงินจริงได้ ต้องตรวจบน staging และยืนยัน QR/ข้อมูลบัญชีก่อน

## โครงสร้างที่ต้องรักษา

```text
โฟลเดอร์เว็บไซต์/
├── portal-private/       ← อยู่นอก public_html; ห้ามเปิดจากเว็บได้
│   ├── config.example.php
│   ├── config.php        ← สร้างบนโฮสต์เอง; ไม่อยู่ใน ZIP
│   ├── lib.php
│   ├── schema.sql
│   └── install.php       ← รันผ่าน CLI เท่านั้น
└── public_html/
    ├── .htaccess
    ├── .user.ini
    ├── api.php
    ├── index.html
    ├── theme.css
    ├── app.js
    └── assets/
```

`api.php` อ้างถึง `../portal-private/lib.php` หากจัดวางคนละตำแหน่งต้องแก้เส้นทางให้ตรง ห้ามย้าย `config.php` หรือไฟล์ SQL เข้า `public_html` อย่าใช้การอัปโหลดทั้งโปรเจกต์ขึ้นเว็บ เพราะมีฐานข้อมูลในเครื่อง ไฟล์ทดสอบ และไฟล์พัฒนา

## ก่อนอัปโหลด

1. สร้างเว็บไซต์ staging หรือ subdomain แยกจากเว็บที่ใช้งานอยู่ กำหนด document root ให้เป็น `public_html` ของ staging อย่าทับเว็บเดิม
2. ใน hPanel เลือก PHP 8.2 ขึ้นไป และมีส่วนขยาย PDO MySQL, mbstring, fileinfo, OpenSSL และ session เปิดใช้งาน ฐานข้อมูลต้องใช้ InnoDB และ utf8mb4
3. สร้าง MySQL database และ database user สำหรับเว็บไซต์นี้โดยเฉพาะ เก็บชื่อฐานข้อมูล ชื่อผู้ใช้ รหัสผ่าน และ database host จาก hPanel อย่าใช้ root และอย่าส่งรหัสผ่านในแชต
4. เปิด SSL และ Force HTTPS สำหรับโดเมนจริง ตรวจว่า HTTP เปลี่ยนไป HTTPS ก่อนตั้งค่า `origin` เป็น URL จริง ต้องเป็น scheme + hostname (+ port เฉพาะเมื่อใช้จริง) โดยไม่มี path หรือ `/` ท้าย
5. สำรองเว็บและฐานข้อมูลปลายทางก่อนเปลี่ยนไฟล์ แม้ปลายทางจะดูว่างอยู่ก็ตาม

## สร้างชุดไฟล์

รันจากโฟลเดอร์โปรเจกต์บนเครื่องพัฒนา:

```sh
npm --prefix prototype run build:css
python3 tools/build_hostinger.py --output deploy/hostinger-release-v1.zip
```

สคริปต์คัดเฉพาะไฟล์ frontend ที่ใช้งาน, assets, API และไฟล์ PHP ที่อนุญาต ไม่รวม `data/`, `.env`, `config.php`, `node_modules`, ภาพหน้าจอ หรือไฟล์ทดสอบ ตรวจ CRC ของ ZIP และ SHA-256 ของสมาชิกทุกไฟล์ พร้อม `release-manifest.json` หากชื่อ ZIP มีอยู่แล้วสคริปต์จะไม่เขียนทับ ให้ใช้ชื่อรุ่นใหม่

## อัปโหลดและตั้งค่า

1. แตก ZIP บนเครื่องแล้วตรวจโครงสร้างด้านบน อัปโหลดเนื้อหาของ `public_html/` ไป document root ของ staging และ `portal-private/` ไปโฟลเดอร์ข้างเคียงนอก document root ด้วย File Manager หรือ SFTP
2. คัดลอก `portal-private/config.example.php` เป็น `portal-private/config.php` แล้วกรอก `dsn`, `db_user`, `db_password`, `origin`, `admin_password_hash`, `secure_cookie` ตามตัวอย่าง ใช้รหัสผ่านผู้ดูแลที่ยาวและไม่ซ้ำเว็บไซต์อื่น สร้าง hash ด้วย `password_hash()` ตามคำสั่งของ backend และไม่ใส่รหัสผ่าน plaintext แทน hash ตั้ง `secure_cookie` เป็น `true` บน HTTPS จริง
3. จำกัดสิทธิ์ไฟล์ config ให้ผู้ใช้โฮสต์อ่านได้เฉพาะที่จำเป็น เช่น `600` เมื่อสภาพแวดล้อมอนุญาต อย่าตั้งสิทธิ์เป็น `777`
4. รัน installer ผ่าน SSH/Terminal ของโฮสต์ (แทนเส้นทาง assets ให้ตรงกับ document root จริง): `php portal-private/install.php /abs/public_html/assets` ตัวติดตั้งทำงานซ้ำได้โดยไม่ล้างข้อมูล ตั้ง `PORTAL_CONFIG` เฉพาะเมื่อต้องใช้ config จากตำแหน่งอื่น ห้ามนำ installer มาเปิดผ่าน URL หากไม่มี SSH ต้องเตรียมขั้นตอนติดตั้งผ่านผู้ดูแลโฮสต์ก่อนดำเนินการ ไม่ควรเปิด endpoint ติดตั้งสาธารณะเพื่อแก้ปัญหานี้
5. หากมีข้อมูลเดิมใน SQLite ให้ใช้ `tools/export_sqlite.py` สร้างไฟล์ย้ายข้อมูลจากสำเนา SQLite แล้วนำเข้าด้วย CLI `portal-private/restore.php /PRIVATE/PATH/portal-migration.json --confirm-empty` (ใช้ฐานข้อมูลปลายทางที่ยังว่าง) ตรวจจำนวนรายการ ยอดเงิน สถานะ ไซซ์เสื้อ หมายเลขโต๊ะ สลิป โปสเตอร์ และประวัติให้ตรงก่อนใช้งาน ห้ามเปิดระบบเดิมและใหม่รับรายการพร้อมกันระหว่างย้าย
6. ตรวจ `post_max_size` ≥ 8M, `upload_max_filesize` ≥ 5M, `memory_limit` ≥ 128M การส่งสลิป/โปสเตอร์ใช้ base64 JSON ซึ่งใหญ่กว่าไฟล์ต้นฉบับประมาณหนึ่งในสาม `.user.ini` อาจใช้เวลาสักครู่จึงมีผล และโฮสต์อาจจำกัดค่าบางอย่าง
7. ไม่ต้องติดตั้ง Node.js บนโฮสต์ CSS ถูก build มาจากเครื่องพัฒนาแล้ว

## ตรวจรับบน staging ก่อนเปิดจริง

- หน้าแรกและเมนูทุกหน้าแสดงเหมือนรุ่นเดิมบนมือถือและคอมพิวเตอร์ ไม่มีรูปหรือฟอนต์หาย
- `GET /api/settings`, `/api/posters`, `/api/tables` ได้ JSON และการเรียก API ไม่เจอหน้า 404 ของโฮสต์ หากพบ ให้ตรวจ `.htaccess` และ document root
- เปิด `/portal-private/config.php`, `/schema.sql`, `/data/donations.sqlite3` ไม่ได้ และต้องไม่ปรากฏรายชื่อไฟล์ในโฟลเดอร์
- เข้าผู้ดูแลได้เฉพาะรหัสที่ถูกต้อง session cookie เป็น HttpOnly/Secure/SameSite และออกจากระบบแล้วเปิดข้อมูลผู้ดูแลไม่ได้
- จองโต๊ะเดียวกันพร้อมกันสองหน้าจอ สำเร็จเพียงรายการเดียว ยกเลิกแล้วคืนโต๊ะ และไม่สามารถคืนสถานะไปทับโต๊ะของรายการอื่น
- เสื้อหลายไซซ์ รับเอง/จัดส่ง 50 บาท คำนวณยอดถูกต้องและบังคับที่อยู่เมื่อจัดส่ง
- แก้ข้อมูลผู้จองผ่านแอดมินแล้วมีประวัติ ยอดรวมและยอดแต่ละประเภทถูกต้อง รวมข้อมูลเกิน 500 รายการ
- สลิปที่ไม่มีสิทธิ์เข้าถึงไม่ได้ สลิปซ้ำถูกปฏิเสธ ไฟล์เกิน 5 MB ถูกปฏิเสธ และ API ไม่เปิดเผย stack trace หรือรหัสผ่าน
- แก้ข้อความแบนเนอร์ ขนาดตัวอักษร ราคา QR และโปสเตอร์แล้วรีโหลด/เข้าสู่ระบบใหม่ข้อมูลยังอยู่ โปสเตอร์สลับทุก 5 วินาที
- ดาวน์โหลด E-ticket โต๊ะ/เสื้อได้บนมือถือ ตรวจตัวอักษรไทย สถานะ ชื่อ รายการและเลขอ้างอิง 6 หลัก หากใช้เป็นหลักฐานเข้างานหรือรับเสื้อ ต้องมีขั้นตอนตรวจสถานะล่าสุดและป้องกันใช้ซ้ำที่หน้างาน
- บันทึกภาพหน้าจอผลตรวจและผล API โดยไม่รวมข้อมูลส่วนตัวหรือรหัสติดตาม

## สำรองและทดสอบกู้คืน

ฐานข้อมูลมีทั้งรายการและไฟล์สลิป/โปสเตอร์ จึงต้องสำรองฐานข้อมูลแบบครบถ้วน พร้อมโฟลเดอร์ `portal-private` และ release ZIP เก็บสำเนาแยกจาก document root และจำกัดสิทธิ์การเข้าถึง

- ใช้ hPanel/phpMyAdmin export ฐานข้อมูลแบบ SQL ครบทั้ง schema และ data หรือใช้ `portal-private/backup.php` ผ่าน CLI ตามวิธีใช้ของสคริปต์ ไฟล์สำรองของเครื่องมือนี้เป็น JSON พร้อม binary แบบ base64 และต้องเก็บเป็นข้อมูลลับ หลีกเลี่ยงคำสั่งที่ใส่รหัสผ่านเป็น argument ซึ่งอาจปรากฏในประวัติ/รายชื่อ process
- กำหนดสำรองอัตโนมัติตามปริมาณรายการ และสำรองก่อนอัปเกรดทุกครั้ง อย่าพึ่งพาสำเนาบนเซิร์ฟเวอร์เดียวเพียงชุดเดียว
- ทดสอบ restore ลง **ฐานข้อมูลใหม่แยกต่างหาก** ด้วย `portal-private/restore.php` และอาร์กิวเมนต์ไฟล์สำรอง พร้อม `--confirm-empty` ตามวิธีใช้ของสคริปต์ ตัวเลือกนี้ยืนยันว่าปลายทางต้องว่าง แล้วเปิด staging ด้วย config ของฐานข้อมูลนั้น เปรียบเทียบจำนวนรายการ ยอดเงิน เลขอ้างอิง สถานะ และดาวน์โหลดสลิปตัวอย่าง
- บันทึกเวลาที่สำรองได้ล่าสุดและเวลาที่ใช้กู้คืน อย่าทดลอง restore ทับฐานข้อมูลจริง
- การ rollback ต้องใช้ release และฐานข้อมูลที่เข้ากัน หากเปิดรับรายการหลังสำรองแล้ว ต้องเก็บรายการใหม่ก่อน rollback เพื่อไม่ให้ข้อมูลหาย

## เปิดใช้งานจริง

เปิดได้เมื่อผ่าน staging, backup/restore และผู้จัดยืนยัน QR/ชื่อบัญชี/ราคา/วันเวลาแล้วเท่านั้น รุ่นปัจจุบันใช้บัญชีและ QR ที่แอดมินตั้งไว้ ไม่มีสวิตช์โหมดทดลอง หากไม่อัปโหลด QR จะแสดงรายละเอียดบัญชีสำหรับโอนเงินแทน ขณะย้ายให้หยุดรับรายการชั่วคราว ย้ายข้อมูลรอบสุดท้าย ตรวจยอด แล้วจึงเปิด URL จริง

หลังเปิด ตรวจ API, login, การส่งสลิป และข้อผิดพลาดของ PHP โดยหลีกเลี่ยงการบันทึกชื่อ/เบอร์/ที่อยู่/token ลง log เก็บระบบ Python และต้นฉบับไว้สำหรับอ้างอิง แต่ไม่เปิดรับรายการซ้อนกับระบบใหม่

## ขอบเขตที่ยังต้องตรวจบนโฮสต์

การสร้าง ZIP และทดสอบในเครื่องไม่ยืนยันการตั้งค่า hPanel, PHP extensions, MySQL privileges, SSL, DNS, quota, งานสำรองอัตโนมัติ หรือภาระผู้ใช้สูงสุดของบัญชีจริง ต้องตรวจรายการเหล่านี้บน staging ก่อนเปิดรับผู้ใช้จริง

## ย้ายข้อมูลจาก Python / SQLite

ไม่ต้องย้ายหากจะเริ่มระบบใหม่โดยไม่มีรายการเดิม หากมีรายการที่ต้องเก็บ ให้หยุดรับรายการเดิมชั่วคราว สำรอง SQLite และ export แบบอ่านอย่างเดียวบนเครื่อง:

```sh
python3 tools/export_sqlite.py /PRIVATE/PATH/donations.sqlite3 /PRIVATE/PATH/portal-migration.json
```

ไฟล์ JSON มีข้อมูลส่วนตัวและสลิปทั้งหมด ต้องเก็บนอกเว็บและโอนผ่านช่องทางส่วนตัว ตัวส่งออกเก็บเลขอ้างอิงเดิม hash รหัสติดตาม ยอด สถานะ สลิป การตั้งค่า และโปสเตอร์ รวม donations รุ่นเก่าเป็นรายการ donate ในระบบใหม่ โดยแปลง approved เป็น confirmed และเริ่มต้นปิดโหมดเงินจริง

สร้าง **ฐานข้อมูลใหม่ว่าง** ตั้ง config ให้ชี้ฐานข้อมูลนั้น แล้วรัน `php portal-private/restore.php /PRIVATE/PATH/portal-migration.json --confirm-empty` ก่อนรัน install.php ตัว restore จะสร้าง schema เองและปฏิเสธปลายทางที่มีข้อมูล จึงไม่เขียนทับรายการเดิม ตรวจจำนวน/ยอด/สถานะ/สลิป/รหัสติดตามก่อนเปลี่ยนเว็บไซต์มาฐานข้อมูลใหม่

คำสั่งสำรอง: `php portal-private/backup.php /PRIVATE/PATH/backup-YYYYMMDD.json` ไฟล์ต้องเป็นชื่อใหม่ ส่วนการกู้คืนใช้ restore.php ตามด้านบน ไม่ย้าย session ผู้ดูแล ต้องเข้าสู่ระบบใหม่หลังย้าย

## การแก้ไขและใช้ตั๋ว

รุ่น PHP เพิ่มปุ่มแก้ไขข้อมูลในรายการแอดมิน ต้องระบุเหตุผล เก็บประวัติทุกครั้ง และรักษาราคาขณะจอง เว้นแต่เลือกใช้ราคาปัจจุบัน การยกเลิกรายการคืนโต๊ะโดยเก็บประวัติไว้ เมื่อตรวจตั๋วหน้างานให้ค้นเลขอ้างอิงในรายการ เปิดแก้ไข และใช้ปุ่มบันทึกใช้ตั๋ว/รับเสื้อ ระบบยอมให้ใช้ได้ครั้งเดียวเฉพาะรายการยืนยันแล้ว การใช้ตั๋วถือว่ารับสิทธิ์ครบทั้งรายการ (เช่น เสื้อทุกตัวในรายการ) ไม่รองรับการรับบางส่วน

## ผังโต๊ะรุ่น A–G

ผังปัจจุบันเปิดจอง 61 โต๊ะ (A/B แถวละ 8, C–G แถวละ 9) และแสดง VIP 2 โต๊ะสำหรับแขกพิเศษซึ่งไม่เปิดจอง รหัสภายในยังเป็นตัวเลขเดิม 1–61 จึงไม่แก้เลขอ้างอิงหรือเขียนทับรายการจองเดิม การแสดงชื่อโต๊ะและตั๋วเปลี่ยนเป็น A1–G9 หากย้ายข้อมูลที่เคยมีโต๊ะ 62–100 ต้องจัดตำแหน่งใหม่กับผู้จัดก่อนเปิดจริง ข้อมูลเดิมจะถูกเก็บไว้และไม่แปลงเป็น VIP อัตโนมัติ

## ตรวจสภาพแวดล้อมก่อนเปิดเว็บ

หลังตั้ง config และสร้าง/กู้คืนฐานข้อมูลแล้ว รัน `php portal-private/check.php` เครื่องมือนี้อ่านอย่างเดียวและไม่แสดงรหัสผ่าน ตรวจ PHP/extensions, HTTPS/cookie, password hash, การเชื่อมต่อ DB, InnoDB/utf8mb4, packet size, บัญชี 4 ประเภท และหมายเลขโต๊ะเดิมนอกผัง ผล PASS ของ CLI ยังต้องตรวจ PHP ผ่านเว็บ, .htaccess, SSL/DNS และการส่งไฟล์จริงบน staging อีกครั้ง

บนเครื่องพัฒนาใช้ `python3 tools/build_hostinger.py --check-only` เพื่อตรวจรายการไฟล์โดยไม่สร้าง ZIP รุ่นปัจจุบันไม่มีสวิตช์โหมดทดลองในแอดมิน การส่งรายการทำงานตามระบบปัจจุบัน ช่อง `payment_live` ที่อาจมีในข้อมูลเก่าเก็บไว้เพื่อรองรับข้อมูลเดิม ไม่ใช่สวิตช์ปิดรับรายการ

### เลือกฐานข้อมูลต้นทางให้ถูกชุด

ณ การตรวจครั้งนี้ เว็บพรีวิวพอร์ต 8082 ใช้ `/private/tmp/portal-preview-preserved-data/donations.sqlite3` มีค่าตั้งบัญชี/QR ล่าสุด ส่วน `data/donations.sqlite3` เป็นฐานข้อมูลรุ่นเก่ากว่าและมีรายการต่างกัน ห้ามถือว่าสองไฟล์นี้เป็นสำเนาเดียวกันหรือย้ายทับกันโดยอัตโนมัติ ต้องเลือกชุดข้อมูลและตรวจยอดก่อนย้ายจริง

โฟลเดอร์ /private/tmp ไม่ควรใช้เป็นที่เก็บถาวรหรือสำรองเพียงแห่งเดียว ก่อนย้ายจริงให้เก็บสำเนาที่ตรวจแล้วในที่เก็บส่วนตัวถาวร และกำหนดช่วงหยุดรับรายการสำหรับการย้ายรอบสุดท้าย ไฟล์ ZIP เก่ารุ่น v1–v5 ไม่รวมการแก้ไขล่าสุดทั้งหมด จึงไม่ควรใช้ติดตั้งรุ่นปัจจุบัน
